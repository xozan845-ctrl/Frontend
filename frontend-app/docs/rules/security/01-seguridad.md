# 01 — Seguridad del cliente

Aplica a: sesión, almacenamiento local, plantillas, configuración, dependencias y
datos de entrada.

| ID     | Regla                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| ------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-SE-1 | **Transporte y almacenamiento de sesión (JWT en cabeceras)**: la autenticación viaja en la cabecera `Authorization: Bearer <jwt>` mediante un interceptor; **no se usan cookies**. El **access token** vive **en memoria** (nunca en `localStorage`); el **refresh token** se persiste (`sessionStorage` como opción preferida; `localStorage` solo con "recordarme") y se renueva por **rotación**, con **revocación** por `jti`. `localStorage` se reserva para estado **no sensible** (carrito, wishlist, tema, recientes, reseñas). |
| R-SE-2 | **Sin secretos en el bundle**: `environment.ts`/`environment.prod.ts` solo contienen configuración pública (URL base, endpoints, flags). Prohibido commitear claves, tokens o contraseñas; los secretos viven en el proveedor de despliegue.                                                                                                                                                                                                                                                                                            |
| R-SE-3 | **Sanitización (XSS)**: prohibido `bypassSecurityTrust*` sin justificación escrita en el PR; los enlaces `[innerHTML]` solo reciben contenido propio o sanitizado. El texto de usuario se interpola, nunca se concatena en HTML.                                                                                                                                                                                                                                                                                                        |
| R-SE-4 | **Sin datos sensibles en consola/logs**: prohibido `console.log` de tokens, credenciales o PII; los errores se registran sin volcar el payload del usuario.                                                                                                                                                                                                                                                                                                                                                                             |
| R-SE-5 | **Dependencias**: `npm audit --audit-level=high` debe salir sin vulnerabilidades `high`/`critical` (gate `R-QA-6`). Las actualizaciones se hacen por PR atómico, no por edición manual del lockfile.                                                                                                                                                                                                                                                                                                                                    |
| R-SE-6 | **Entrada no confiable**: todo dato que llega por query params, `localStorage` o respuesta de API se valida/normaliza antes de usarse; los formularios validan en cliente además de confiar en el backend.                                                                                                                                                                                                                                                                                                                              |
| R-SE-7 | **Terceros y enlaces**: los enlaces externos abren con `rel="noopener noreferrer"`; los scripts/recursos de terceros se cargan solo por https y con propósito justificado.                                                                                                                                                                                                                                                                                                                                                              |
| R-SE-8 | **Tráfico solo al backend configurado**: ninguna petición sale hacia hosts distintos de `environment.apiUrl`; prohibido hardcodear URLs (`R-AR-11`).                                                                                                                                                                                                                                                                                                                                                                                    |
| R-SE-9 | **Endurecimiento XSS (defensa en profundidad)**: como el token es accesible por JS (`R-SE-1`), se mantiene una **CSP estricta** (sin `unsafe-inline`/`unsafe-eval`), se minimizan scripts y recursos de terceros (con SRI si aplica) y no se usa `innerHTML` con datos de usuario (`R-SE-3`). Los tokens **nunca** viajan en URL, query params ni logs.                                                                                                                                                                                 |

## Notas

- **Decisión (ADR-10)**: se usa **JWT en la cabecera `Authorization`**, no cookies.
  Compromiso asumido: el cliente debe tener el token accesible por JS, así que
  **XSS es la amenaza principal** (no hay `HttpOnly` que proteja). Se compensa con
  access token de vida corta **en memoria**, refresh **rotativo y revocable** por
  `jti`, CSP estricta y minimización de terceros (`R-SE-9`).
- **Deuda actual (`R-SE-1`)**: `AuthStore` guarda `{ user, token }` en
  `localStorage` bajo `ecom_auth_data`. Registrado en AUDIT como deuda:
  al implementar la sesión, mover el **access token a memoria** y separar el
  **refresh token** persistido.
- El interceptor de auth (`auth.interceptor.ts`) ya añade `Authorization: Bearer`
  cuando `authType: 'bearer'` y soporta `withCredentials`; esa es la ruta de
  `R-SE-1`. Las cookies quedan descartadas por decisión.
