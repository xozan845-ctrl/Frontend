# 01 — Arquitectura

Aplica a: organización del código, dependencias entre capas, conexión con el
backend, gestión de estado, navegación, formularios y ciclo de vida de la SPA.

La estructura es **empresarial por capas de primer nivel** (ADR-12):

```text
src/app/
├── core/        # infraestructura transversal · SIN UI · NO depende de features
├── shared/      # presentación/utilidades reutilizables · sin lógica de negocio
├── layout/      # chrome de la app (navbar/header, footer, drawers)
└── features/    # dominios de negocio (clean/hexagonal dentro de cada uno)
```

## Organización y dependencias

| ID      | Regla                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 |
| ------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| R-AR-1  | **Feature-first en cuatro capas**: la app se organiza en `src/app/core/`, `src/app/shared/`, `src/app/layout/` y `src/app/features/<feature>/` (`auth`, `cart`, `home`, `plans`, `products`, `wishlist`). Cada feature agrupa `pages/` (destinos de ruta), `components/` (presentacionales internos), `state/`, `services/`, `repositories/`, `adapters/`, `models/`, `constants/`, `mocks/` y `<feature>.routes.ts`. Prohibido crear carpetas por tipo técnico en la raíz de `app/` (`services/`, `components/`, …).                                                                                                 |
| R-AR-2  | **Dirección de dependencias**: `core/`, `shared/` y `layout/` **no** importan de `features/`; `core/` **no** depende de `shared/` ni de `layout/`; `shared/` puede depender de `core/`. Un feature consume a otro solo por su **API pública** (`../frontend/01-arquitectura-limpia.md`, `R-CX-6`), nunca por rutas internas. `app.config.ts` y `app.routes.ts` son el único punto de composición.                                                                                                                                                                                                                     |
| R-AR-3  | **Puertos e inyección de dependencias (DIP)**: toda dependencia a infraestructura (HTTP, almacenamiento, APIs externas) se declara como **interfaz + `InjectionToken`** en `repositories/`, se implementa en `services/` y se cablea en `app.config.ts` (`{ provide: PRODUCT_REPOSITORY, useClass: ProductService }`). Los consumidores dependen del token (`inject(PRODUCT_REPOSITORY)`), no de la clase concreta. Los puertos **transversales** (auth, cart, products) se cablean en `app.config.ts`; los puertos de un feature **lazy y autocontenido** pueden cablearse en los `providers` de su ruta (`ADR-18`). |
| R-AR-4  | **Adapters / capa anticorrupción (ACL)**: ninguna respuesta externa entra cruda al dominio. Se normaliza en `adapters/` con funciones puras `adapt*FromBackend` (tolerantes a `camelCase`/`snake_case`, envelopes `{ data }`/`{ items }`/`{ results }` y tipos string numéricos). El modelo de dominio (`models/*.model.ts`) es estable y no conoce esos formatos.                                                                                                                                                                                                                                                    |
| R-AR-5  | **Estado con NgRx Signals**: el estado compartido vive en un `signalStore` (`withState`/`withComputed`/`withMethods`/`withHooks`). Los derivados se calculan en `withComputed` (nunca en la plantilla), las mutaciones en `withMethods` con `patchState`, y la persistencia en `withHooks`. Prohibido crear estado de servidor con `BehaviorSubject` o servicios "god".                                                                                                                                                                                                                                               |
| R-AR-6  | **Componentes standalone y rutas lazy**: los componentes son `standalone` con sus dependencias en `imports`; cada feature expone sus rutas en `<feature>.routes.ts` y se carga con `loadChildren`/`loadComponent` (`R-AR-12`). Prohibido importar estáticamente un feature desde `app.component.ts` o desde otra ruta.                                                                                                                                                                                                                                                                                                |
| R-AR-7  | **Formularios reactivos tipados**: todo formulario de negocio usa `ReactiveFormsModule` + `FormBuilder` (preferentemente `nonNullable.group`) con `Validators` explícitos. Prohibido `FormsModule`/`ngModel` para lógica de negocio.                                                                                                                                                                                                                                                                                                                                                                                  |
| R-AR-8  | **Sin acceso a red en componentes**: `HttpClient` se inyecta **solo** en `services/`; los componentes leen y mutan estado a través de stores o servicios. Ningún componente llama a `HttpClient` directamente.                                                                                                                                                                                                                                                                                                                                                                                                        |
| R-AR-9  | **Errores traducidos y notificados**: los errores de API se capturan en el servicio/store, se traducen a un mensaje de dominio y se muestran con `NotificationService`. Prohibido `alert`, `confirm` o `prompt` nativos y prohibido dejar errores sin notificar al usuario.                                                                                                                                                                                                                                                                                                                                           |
| R-AR-10 | **Ciclo de vida de suscripciones**: en componentes, todo `Observable` se libera con `takeUntilDestroyed`/`takeUntil` o se consume en plantilla con `async`/signals; los listeners de `window`/`document` se retiran en `ngOnDestroy`. Prohibido un `subscribe` sin estrategia de liberación.                                                                                                                                                                                                                                                                                                                          |
| R-AR-11 | **Configuración por entorno**: la URL base y los endpoints viven en `src/environments/` y `DEFAULT_API_CONFIG` (`core/config/api.config.ts`); prohibido hardcodear hosts, puertos o rutas de API en componentes o servicios.                                                                                                                                                                                                                                                                                                                                                                                          |
| R-AR-12 | **Rutas por feature**: cada feature declara sus rutas en `src/app/features/<feature>/<feature>.routes.ts` (páginas cargadas con `loadComponent`); `app.routes.ts` las **compone** (importa los arrays de rutas del feature y los extiende, o usa `loadChildren`). Prohibido importar componentes de página de forma estática en `app.routes.ts` ni declarar sus rutas inline.                                                                                                                                                                                                                                         |
| R-AR-13 | **Frontera de `core/`**: `core/` contiene solo infraestructura transversal sin UI ni reglas de negocio (tokens/config de API, adapters genéricos de envelopes, servicios de aplicación sin UI como SEO/configuración/notificaciones). `core/` **no** importa `features/`; lo específico de un dominio vive en su feature.                                                                                                                                                                                                                                                                                             |

## Qué vive en cada capa

| Capa        | Contenido permitido                                                                                                                             | Prohibido                                                                      |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| `core/`     | `config/`, `tokens/`, `models/` genéricos, `services/` de aplicación sin UI, `interceptors/`/`guards/` **genéricos** (sin depender de features) | Componentes/plantillas, lógica de negocio, importar features                   |
| `shared/`   | `ui/` (presentacionales), `directives/`, `pipes/`, `constants/`                                                                                 | Estado de un feature, reglas de negocio, importar features                     |
| `layout/`   | `navbar/`, `footer/`, drawers/chrome visual                                                                                                     | Reglas de negocio; inyectar stores directamente si puede resolverse con inputs |
| `features/` | Todo el dominio de negocio y sus capas internas                                                                                                 | Importar rutas internas de otro feature                                        |

## Notas

- La regla de precio/dinero del backend (centavos) **no aplica** aquí: el
  frontend recibe y muestra montos ya formateados o `number`; aun así, todo
  cálculo de carrito redondea a 2 decimales antes de mostrarse (`R-U-6`).
- La separación **Smart/Dumb** se detalla en
  [`../frontend/02-solid-srp.md`](../frontend/02-solid-srp.md) (`R-SO-8`).
- La frontera entre features (`R-CX-6`) y las API públicas
  (`public-api.ts`/`public-ui.ts`) se detallan en
  [`../frontend/01-arquitectura-limpia.md`](../frontend/01-arquitectura-limpia.md).
